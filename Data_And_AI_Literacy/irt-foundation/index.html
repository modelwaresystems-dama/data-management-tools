IRT foundation & response schema

What the DLK pilot must capture from day one so a real IRT model can be fitted later and nothing has to be re-collected — plus the model choice, the synthetic-seeding and recalibration pipeline, and a working Graded Response Model demo so the maths is proven, not asserted.

Where IRT sits — it does not replace the mastery gates

IRT — the analytics & selection layer
  • Estimates a continuous ability θ per capability (per evidence channel) from the item responses.
  • Gives the measurement uncertainty (standard error of θ) — the "uncertainty" term in next-item priority.
  • Gives item information at the current θ — which drives "ask the question that most reduces uncertainty."
Evidence gates — the mastery layer (unchanged)
  • The defensible mastery band (M0–M5) still comes from the cumulative evidence-channel gates (the D1 fix).
  • Mastery needs evidence types (knowledge → judgement → practical → workplace), not just a high θ.
  • Your spec is explicit: the analytical index "does not determine mastery by itself." θ is analytics; gates are the claim.

So θ answers "how able, and how sure are we?" and selects the next item; the gates answer "what can we defensibly claim?". The pilot's rules engine uses θ's SE and information for selection today; the GRM below slots in behind the same interface once calibrated.

Two supporting records sit beside this one: item_parameters (item_id, item_version, calibration_id, model, a, b₁…b₅, n_responses, cohort = synthetic|real|mixed, fit stats, status) and ability_estimate (learner_id, capability_id, channel, θ, SE, n_items, calibration_id, updated_at). Both are regenerated by a calibration run; the response records above are the immutable source they are computed from.

The model

Model familyrecommended default
Graded Response Model (GRM), one latent trait per capability. The 0–5 rubric is ordinal with more-than-two ordered categories, which is exactly what a polytomous ordinal model is for — a dichotomous model (Rasch/2PL) would throw away the partial-credit information. Per-capability unidimensional keeps it interpretable and matches your "per capability store"; a multidimensional model is a later refinement once there is enough cross-loading data.

Each item has a discrimination a and ordered thresholds b₁ … b₅ (for 6 categories). The boundary probability is P*ₖ(θ) = 1 / (1 + e−a(θ−bₖ)), the category probability is Pₖ = P*ₖ − P*ₖ₊₁, and item information is Iᵢ(θ) = Σₖ (P*ₖ′ − P*ₖ₊₁′)² / Pₖ. Ability is estimated as the posterior mean over a θ grid (EAP) with its standard deviation as the SE. The demo below runs exactly these formulas.

θ → indicative band is shown for orientation only; the defensible band always comes from the evidence gates, so a high θ on knowledge items alone can never, by itself, produce M4/M5.

Synthetic seeding & recalibration pipeline

1 · Author items with provisional parameters. Subject-matter authors set a rough discrimination and thresholds per item (or inherit from a sibling item). These are priors, not truths.
2 · Generate synthetic examinees. Draw θ from a plausible population distribution per role, simulate responses through the GRM, and seed the engine so adaptive selection and θ-estimation work on day one — before any real DLK data exists. Every synthetic response carries synthetic_flag = true.
3 · Run the DLK pilot on the rules engine. Real learners generate real, flagged-real responses captured in the schema above. The rules engine selects items using θ-SE and information; mastery comes from the gates.
4 · Calibrate on real responses. Once an item has enough real responses, estimate its true a/bₖ (marginal maximum likelihood / EM) from real data, writing a new item_parameters row with cohort = real. Re-estimate every learner's θ against the new parameters via calibration_id.
5 · Recalibrate on triggers. Re-run when an item accumulates N new responses, when it is edited (new item_version), when content/regulation changes, or on a fixed cadence. Retire items with poor fit or discrimination.
The non-negotiable caveat Synthetic data bootstraps the priors so the engine can run cold — it cannot validate real-world item difficulty, discrimination, or differential item functioning. Nothing high-stakes (an M4+/professional claim, an Article-4 record) may rest on synthetic-seeded parameters. Item parameters are "provisional" until calibrated on sufficient real responses, and the UI should label them so. This is why synthetic_flag and cohort exist and why they can never be conflated.
